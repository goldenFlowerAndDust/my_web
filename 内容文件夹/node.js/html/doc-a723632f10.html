process、.env、loadEnvFile —— 一次讲透

数据来源：课堂/第十二节课——完整项目/学生管理系统/环境变量与进程.md · 更新于 2026-11-24

这篇解决三个困惑：① process 到底是什么；② loadEnvFile 干了什么；③ 它和 fs.readFile 差在哪、自己写要怎么解析。文中结论都在 Node 24 上实测过。

一、process 是 Node 的全局对象

代表当前这个 Node 进程。不用 require、不用 import，任何文件里直接能写。

浏览器里对应的是 window；Node 里就是 process。

成员是什么例子
process.env环境变量对象（普通对象，值全是字符串）process.env.DB_USER
process.argv命令行参数数组node a.mjs 张三 → ['node','a.mjs','张三']
process.cwd()当前工作目录D:\...\实操
process.versionNode 版本v24.21.0
process.platform系统win32
process.exit(1)退出进程，1 表示失败
process.loadEnvFile(path)加载 .env 文件（20.12+）见下文

二、process.env 就是一个普通对象

console.log(process.env.DB_USER)   // undefined（还没加载时）

它初始只有系统/终端里已有的环境变量。.env 文件里的内容不会自动进来，要有人把它读进来。

两条铁律（实测）：

规则现象
值全是字符串DB_PORT=3306 → process.env.DB_PORT === '3306'（不是数字）
不覆盖已存在的变量终端里先 set DB_USER=预设值，再加载 .env，process.env.DB_USER 仍是「预设值」

所以代码里常见这种写法：

port: Number(process.env.DB_PORT) || 3306      // 字符串要转数字

三、loadEnvFile 到底做了什么

process.loadEnvFile('./.env')

它做三件事：读文件 → 按 KEY=VALUE 解析 → 写进 process.env。

关键点（很多人误会的地方）：

const ret = process.loadEnvFile('./.env')
console.log(ret)   // undefined —— 它不返回数据！

它不给你数据，它改的是 process.env。

所以“为什么不用任何操作就能直接用”——因为你用的不是它的返回值，而是本来就在的 process.env，只是被填满了。

实测：

调用前：DB_USER = undefined
返回值：undefined
调用后：DB_USER = "root"

四、.env 文件的格式

# 这是注释，以 # 开头
PORT=3100
DB_HOST=127.0.0.1
DB_PASSWORD="abc=123"     ← 值里可以有 =，也可以包引号
规则说明
一行一个键=值
# 开头是注释空行忽略
键和值之间可以空格会自动 trim
值可以是字符串"abc"、'abc' 的引号会被去掉
不支持嵌套只有一层 KEY=VALUE，不是 JSON

五、和 fs.readFile 的区别

fs.readFileSync('./.env','utf8')process.loadEnvFile('./.env')
返回什么文件全部文本undefined
副作用无写入 process.env
解析你负责它负责
通用性任何文件只认 .env 格式
出错文件不存在 → 抛异常文件不存在 → 抛异常

一句话：loadEnvFile = readFile + 解析 + 塞进 process.env，是专门为 .env 准备的现成实现。

六、自己用 readFile 解析（原理搞清楚）

思路：每行按第一个 = 切成两半 → [键, 值] → 放进对象。

写法 A：for 循环（直观）

import fs from 'node:fs'

const text = fs.readFileSync('./.env', 'utf8')
const obj = {}

for (const line of text.split(/\r?\n/)) {
    const s = line.trim()
    if (!s || s.startsWith('#')) continue      // 跳过空行和注释

    const i = s.indexOf('=')                    // ★ 用第一个 = 切
    if (i < 0) continue

    obj[s.slice(0, i).trim()] = s.slice(i + 1).trim()
}

console.log(obj)   // { PORT: '3100', DB_HOST: '127.0.0.1', ... }

写法 B：Object.fromEntries（简洁）

const obj = Object.fromEntries(
    fs.readFileSync('./.env', 'utf8')
        .split(/\r?\n/)
        .map(l => l.trim())
        .filter(l => l && !l.startsWith('#'))
        .map(l => {
            const i = l.indexOf('=')
            return [l.slice(0, i).trim(), l.slice(i + 1).trim()]
        })
)

Object.fromEntries([[k,v],[k,v]]) → { k: v }，专门把“键值对数组”变成对象。

三个必须注意的细节

细节为什么
用 indexOf('=') 而不是 split('=')密码里可能有 =，只切第一个才是对的
换行用 /\r?\n/Windows 文件是 \r\n，只按 \n 切会留下 \r，密码多个不可见字符
去掉成对引号DB_PASSWORD="abc" 里引号不是密码的一部分

七、加载 .env 的三种方式

方式怎么写谁负责优点缺点
命令行参数node --env-file=.env server.mjsNode 启动时零代码忘带就报错、依赖工作目录
代码里加载process.loadEnvFile(path)你的代码不会忘、可指定绝对路径多一行代码
第三方包import 'dotenv/config'dotenv 包兼容老 Node要装包，内置方法已够用

你现在用的是第二种：process.loadEnvFile(path.join(import.meta.dirname, '.env'))，用 import.meta.dirname 定位，所以不管从哪个目录启动都能找到。

八、ESM（.mjs）相关的小抄

想干的事CJS（.js）ESM（.mjs）
导入require('./a')import a from './a.mjs'（扩展名不能省）
导出module.exports = xexport { x } / export default x
当前目录__dirnameimport.meta.dirname（20.11+）
顶层 await不行可以
内置模块require('fs')import fs from 'node:fs'（node: 前缀可选但推荐）

import path from 'node:path'

    console.warn('[提示] 没找到 .env，将使用默认配置')

const connection = mysql.createPool({
    host: process.env.DB_HOST || '127.0.0.1',
    port: Number(process.env.DB_PORT) || 3306,
    user: process.env.DB_USER || 'root',
    password: process.env.DB_PASSWORD ?? '',

十二、.env 是永久存储吗？（重点）

⚠️ 结论先说

.env 是文件，永久的；process.env 是内存，进程一退出就没了。 loadEnvFile 只做「文件 → 内存」，从不回写文件。

12.1 三个东西，三种生命周期

东西存在哪活多久谁能改
.env 文件磁盘永久只有你手动编辑
process.env内存这个进程活着期间代码随时可改，退出即消失
数据库磁盘永久SQL

✅ 正确理解：持久化的是文件，内存只是启动时的一份副本。 ❌ 错误理解：“我代码里改了 process.env，下次启动还在”——不会。

12.2 实测：两个进程对比

=== 第一个进程 ===
读到 DB_USER = root
设置 TEST_KEY = 我改的临时值
把 DB_USER 改成 = 被我改了

=== 第二个进程（全新启动）===
TEST_KEY = undefined          ← 上一个进程设的，没了
没加载时 DB_USER = undefined   ← 内存是空的
加载 .env 后 DB_USER = root    ← 从文件重新读，还是原值

.env 文件是否被修改: 没有 ✅

🔑 重点：第二个进程里 DB_USER 又变回 root —— 因为第一个进程的修改只活在它自己的内存里。

12.3 什么时候才执行

ab.mjs 顶层的 loadEnvFile(...) 在 它被加载的那一刻执行，不是等 conn.query()：

import { conn } from './ab.mjs'   // ← 这一句就触发了 loadEnvFile
node ab.mjs        # 直接跑：触发
node server.mjs    # server.mjs 里 import 了它：同样触发

✅ 只执行一次：Node 对同一个模块只执行一次，第二次 import 拿的是缓存。所以 .env 不会重复加载，连接池也不会重复创建。

12.4 影响范围（谁看得到）

对象会不会受影响
.env 文件本身❌ 完全不动
当前进程的 process.env✅ 被填充
别的终端 / 别的 node 进程❌ 完全不知道
进程退出后❌ 内存里的值消失
当前进程 spawn 的子进程✅ 会继承（实测：父进程 set 的变量，子进程能读到）

⚠️ 所以“进程树内部能传下去，但进程一结束就断”——不会留到下次启动。

12.5 一句话记住

🎯 .env 是“开机读一次的配置单”

🎯 process.env 是“读进内存的那一份”

🎯 进程结束，内存清单销毁；文件永远是原来的内容

推论：

  • 想改配置 → 改 .env 文件；
  • 想存运行数据（登录状态、计数、业务数据）→ 存数据库；
  • 不要在 .env 里放会变的东西，它只是“启动参数”。
